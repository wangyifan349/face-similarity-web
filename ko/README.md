## 📖 소개

이 프로그램은 이런 종류의 문제를 풉니다: **쿼리 이미지 한 장을 주면, 그것이 누구와 가장 닮았는지 찾아줍니다.** 먼저 이미지에서 얼굴 위치를 검출하고, 각 얼굴마다 고정 길이의 특징 벡터를 추출한 뒤, 두 특징 벡터의 코사인 유사도를 0–100 퍼센트로 환산하여, 마지막으로 유사도 내림차순으로 후보 목록을 정렬해 반환합니다. 퍼센트가 높을수록 두 사진의 얼굴 특징이 비슷합니다. 프로그램 자체는 “동일인인지” 판정을 내리지 않으며, 구체적인 판정 임계값은 사용자가 자신의 샘플로 별도 보정해야 합니다.

프로그램은 두 가지 검색 방식을 제공하며, 서로 독립적으로 사용할 수 있습니다:

- 📤 **업로드 비교** — 한 장의 쿼리 이미지를 이번에 함께 업로드한 여러 후보 이미지와 하나씩 비교합니다. 얼굴 라이브러리를 만들 필요가 없어 임시 대조용으로 적합합니다.
- 🗂️ **얼굴 라이브러리 검색** — 쿼리 이미지 한 장을 서버 얼굴 라이브러리의 전체 이미지와 비교하여, 자동으로 가장 유사한 몇 개를 반환합니다. 고정된 인원 집합에서 찾기에 적합합니다.

두 기능은 페이지의 좌우 두 열에 나란히 배치되며, 시각 레이아웃과 상호작용이 완전히 동일합니다.

이 저장소는 두 가지 엔진 구현을 제공합니다. [두 버전의 차이](#-두-버전의-차이)에 명시된 차이 외에는 기능, API, 페이지 동작이 모두 동일하며, 각각 단일 파일로 되어 있어 검출·특징·평가·Web 서비스 로직이 모두 내장되어 있고 두 번째 모듈에 의존하지 않습니다.

## 🔀 두 버전의 차이

| 비교 항목 | dlib 버전 | InsightFace 버전 |
| --- | --- | --- |
| 📄 파일 | `flask_face_match_v2.py` | `flask_insightface_face_v3.py` |
| ⚙️ 시작 설정 | 명령줄 인자 | **무인자**, 시작 시 대화형으로 얼굴 라이브러리 디렉터리 문의(전달된 인자는 조용히 무시됨) |
| 👁️ 얼굴 검출 | `mmod_human_face_detector.dat`(CNN) 또는 dlib 내장 HOG, 페이지에서 전환 가능 | SCRFD(`det_10g.onnx`), **단일 검출기** |
| 🧬 특징 추출 | dlib ResNet, 128차원 | ArcFace, 512차원 |
| 📍 키포인트 모델 | 필요 (68점, 없으면 5점으로 대체) | 불필요 |
| 📥 가중치 획득 | 수동으로 `.bz2` 다운로드 후 압축 해제 | 첫 실행 시 `insightface`가 자동 다운로드 |
| 📏 점수 스케일 | 같은 인물은 보통 85 이상 | 같은 인물은 보통 75 이상, 다른 사람은 0 근처 |
| 🎛️ 페이지 검출 방식 드롭다운 | 있음 | 없음 |
| ⚡ 하드웨어 가속 | CPU(로컬 검증 환경) | 시작 시 CUDA 자동 탐지, 가능하면 GPU, 아니면 CPU로 폴백 |

> ⚠️ **두 버전의 점수는 서로 직접 비교할 수 없습니다.** 완전히 다른 특징 모델에서 나오므로 스케일은 각자 내부에서만 일관됩니다. 자세한 내용은 [점수 기준](#-점수-기준) 참고.

## ✨ 기능 특성

| 특성 | 설명 |
| --- | --- |
| 📦 **단일 파일 배포** | 두 엔진이 각각 하나의 `.py` 파일로, 두 번째 모듈 없음 |
| 🔀 **두 가지 검색 방식** | 업로드 비교와 얼굴 라이브러리 검색이 병렬로, 서로 의존하지 않음 |
| 🎛️ **이중 검출 모드** | dlib 버전은 「정확(CNN)」과 「빠름(HOG)」 사이에서 전환 가능, 평가 기준 일관 |
| 🧠 **모델 상주** | 모델은 프로세스 안에서 한 번만 로드되고, 모드 전환 시 서비스 재시작 불필요 |
| ⚡ **라이브러리 캐시** | 얼굴 라이브러리는 파일 단위로 특징을 캐시하고, 수정 시각으로 무효화를 판정, 추가·수정·삭제 즉시 반영 |
| 🛡️ **내결함 설계** | 손상되었거나 얼굴이 없는 이미지는 건너뛰고 기록, 전체 검색을 중단하지 않음 |
| 📊 **절대 스케일 시각화** | 유사도 바는 고정 스케일로 그려짐; ⚠️ 음수는 0% 빈 바로 표시되지만 숫자는 실제 부호 있는 점수를 표시 |
| 🔒 **환경변수 없음** | 두 버전 모두 어떤 환경변수도 읽지 않음, 설정 출처가 명확 |
| 🕵️ **경로 비노출** | 얼굴 라이브러리 디렉터리는 서버에만 존재하며, 페이지와 API 모두에 노출·수용되지 않음 |

화면 요점: 좌우 두 열이 같은 너비로 나란히, 페이지 양쪽에 딱 붙음; 파일 선택 후 즉시 썸네일 미리보기 표시; 요청 진행 중 버튼이 로딩 상태로 전환; 가장 유사한 항목은 별도 요약 블록으로 강조; 오류 메시지는 닫을 수 있는 알림 바로 표시.

## ⚙️ 실행 환경

두 버전 모두 Flask, OpenCV, NumPy를 공유하고, 인식 엔진 의존성만 다릅니다:

| 항목 | 최소 요구 | 로컬 검증 버전 |
| --- | --- | --- |
| Python | 3.9 | 3.14.3 |
| Flask | 3.0 | 3.1.3 |
| opencv-python | 4.5 | 5.0.0.93 |
| numpy | 1.23 | 2.4.6 |

| 엔진 | 추가 의존성 | 로컬 검증 버전 |
| --- | --- | --- |
| dlib 버전 | `dlib` | 20.0.1 |
| InsightFace 버전 | `insightface`, `onnxruntime` | 2.0 / 1.30.0 |

Windows, Linux, macOS를 지원합니다. dlib을 제외한 나머지 의존성은 모두 pip으로 직접 설치할 수 있습니다:

```bash
pip install flask opencv-python numpy
# 선택한 엔진에 따라 다음 중 하나를 추가:
pip install dlib                  # dlib 버전
pip install insightface onnxruntime   # InsightFace 버전
```

> 📝 위 표의 「로컬 검증 버전」은 실제로 설치하고 검증한 조합입니다. 코드 자체는 3.9 전용 문법을 쓰지 않으므로, 이론상 하한은 `dlib` / `insightface`의 사용 가능한 wheel이 결정합니다.

### 🔨 dlib 설치 관련

dlib은 일부 플랫폼과 인터프리터 조합에서 사전 컴파일 패키지가 없어, 로컬에 C++ 컴파일 환경이 필요합니다:

| 플랫폼 | 필요 의존성 |
| --- | --- |
| Windows | Visual Studio Build Tools의 「C++를 사용한 데스크톱 개발」 워크로드 |
| Linux | `build-essential`, `cmake` |
| macOS | Xcode Command Line Tools |

소스 컴파일이 실패하면 conda 채널의 사전 컴파일 패키지를 사용할 수 있습니다: `conda install -c conda-forge dlib`.

## 🧠 모델 파일 (가중치 다운로드)

### dlib 버전

dlib 공식 4개 가중치 파일에 의존합니다. **모두 dlib 공식 사이트에서 다운로드하며, 가입·로그인 불필요.**

| 파일 | 용도 | 필수 여부 | 다운로드 | 압축 크기 |
| --- | --- | --- | --- | --- |
| `shape_predictor_68_face_landmarks.dat` | **68점 얼굴 키포인트 예측**. 얼굴 박스 검출 후 특징점을 찾아서 특징 추출 입력으로 사용 | 필수 (없으면 5점으로 대체) | [dlib.net/files](http://dlib.net/files/shape_predictor_68_face_landmarks.dat.bz2) | 약 61 MB |
| `dlib_face_recognition_resnet_model_v1.dat` | **128차원 얼굴 특징 추출**. 모든 유사도 점수는 이 특징 벡터로 계산 | 필수 | [dlib.net/files](http://dlib.net/files/dlib_face_recognition_resnet_model_v1.dat.bz2) | 약 20 MB |
| `mmod_human_face_detector.dat` | **CNN 얼굴 검출기** (MMOD). 「정확(CNN)」 모드에서만 필요, 옆얼굴·작은 얼굴·복잡한 배경 검출률이 HOG보다 훨씬 높음 | 선택 | [dlib.net/files](http://dlib.net/files/mmod_human_face_detector.dat.bz2) | 약 0.7 MB |
| `shape_predictor_5_face_landmarks.dat` | **5점 키포인트 예측**, 68점 버전의 대체. 68점 파일이 없을 때만 자동 사용, 정렬 정밀도 하락 | 선택 | [dlib.net/files](http://dlib.net/files/shape_predictor_5_face_landmarks.dat.bz2) | 약 5.4 MB |

📌 앞의 두 개 중 하나라도 빠지면 프로그램은 동작하지 않습니다(시작 단계에서 바로 예외 발생).

> ⚠️ `mmod_human_face_detector.dat`이 없어도 **우아하게 대체되지 않습니다**: 기본 모드가 CNN이므로, 모델 로드 시 잡히지 않은 `FileNotFoundError`가 발생하고 웹 서비스는 워밍업 단계에서 종료됩니다. 서비스가 이미 실행 중이면 CNN 모드로 전환하는 요청은 **HTTP 500**을 반환합니다. CNN 모드가 필요 없으면 `--hog`로 시작하세요.

### InsightFace 버전

`buffalo_l` 모델 패키지의 두 파일에 의존합니다: `det_10g.onnx`(SCRFD 검출)와 `w600k_r50.onnx`(ArcFace 512차원 특징).

**수동 다운로드 불필요**: 첫 실행 시 `insightface`가 사용자 디렉터리의 `.insightface/models/buffalo_l`에 전체 `buffalo_l` 모델 패키지를 자동 다운로드합니다.

프로그램은 아래 순서로 모델 디렉터리를 찾으며, **그 디렉터리 안에 두 파일이 모두 있어야** 일치로 간주합니다:

1. 스크립트 옆 `insightface_models/buffalo_l/`
2. 스크립트 옆 `models/buffalo_l/`
3. 스크립트 옆 `buffalo_l/`
4. `~/.insightface/models/buffalo_l/` (자동 다운로드 기본 위치)

💡 앞의 세 가지는 모델을 프로그램과 함께 배포해 완전히 오프라인으로 실행할 수 있게 합니다.

📌 어떤 디렉터리가 존재하지만 그 중 하나의 파일이 없으면, 그 디렉터리는 **조용히 건너뛰고** 다음을 시도합니다. 모든 위치가 불완전하면 자동 다운로드로 넘어갑니다. **프로그램은 “어느 파일이 빠졌는지”를 능동적으로 알리지 않습니다.**

오프라인 환경이면, 먼저 인터넷이 되는 기기에서 한 번 실행해 다운로드를 완료한 뒤, `buffalo_l` 디렉터리를 통째로 복사해 위 어느 위치든 두면 됩니다.

### 📂 dlib 가중치 배치 위치와 탐색 순서

프로그램은 먼저 모든 후보 경로를 수집한 뒤 그중 처음으로 사용 가능한 파일을 고릅니다:

1. 스크립트 옆의 `models/` 디렉터리
2. 스크립트가 있는 디렉터리
3. 스크립트가 있는 디렉터리 아래의 임의 하위 디렉터리 (재귀 탐색)
4. `sys.path`의 **모든** 디렉터리 아래의 해당 파일명, 및 그 디렉터리의 `face_recognition_models/models/` 아래의 해당 파일명

> 📝 4번째 단계는 `sys.path`의 순서대로 각 디렉터리를 **번갈아가며 시도**합니다. 즉 `sys.path[0]/<파일>` → `sys.path[0]/face_recognition_models/models/<파일>` → `sys.path[1]/<파일>` → … 순이며, 전체 `sys.path`를 다 훑고 나서 모델 패키지를 찾는 방식이 아닙니다.

모든 위치에서 찾지 못하면 프로그램은 시작 단계에서 바로 예외를 던지고, 어떤 파일이 빠졌는지 명확히 알려줍니다.

🔍 **ASCII 경로 우선**: 후보 결과 중 순수 ASCII 경로가 있으면, 더 앞에 있는 비 ASCII 경로보다 우선 선택됩니다(dlib은 비 ASCII 경로를 열 수 없기 때문). 모든 후보가 비 ASCII면 첫 번째로 되돌아갑니다.

권장 디렉터리 구성:

| 경로 | 용도 | 필수 여부 |
| --- | --- | --- |
| `flask_face_match_v2.py` | dlib 버전 본체 | 필수 |
| `models/` | 가중치 파일 보관, 필수 2개는 여기 | 필수 |
| `face_library/` | 얼굴 라이브러리 디렉터리, `--dir`로 다른 위치 지정 가능 | 선택 |

dlib 가중치를 하나씩 다운로드하는 번거로움을 피하려면 다음 중 하나를 선택하세요:

| [face_recognition_models (PyPI)](https://pypi.org/project/face-recognition-models/) | pip으로 설치하는 모델 패키지, **68점 키포인트와 인식 모델 두 파일 포함**, 설치 후 프로그램이 패키지 내 `models` 디렉터리에서 자동으로 찾음. **CNN 검출기는 포함하지 않음**, 「정확(CNN)」 모드는 별도 다운로드 필요 |
| [face_recognition_models (GitHub 소스 저장소)](https://github.com/ageitgey/face_recognition_models) | 위 모델 패키지의 소스 저장소, 가중치 원 다운로드 설명 포함 |

### 🇨🇳 비ASCII 경로 관련

dlib은 비ASCII 문자가 포함된 경로를 직접 열 수 없습니다. dlib 버전에는 이런 가중치 파일을 자동으로 시스템 임시 디렉터리(`%TEMP%\dlib_face_models\`)에 복제해 로드하는 내장 로직이 있어, 사용자는 신경 쓸 필요가 없습니다. InsightFace 버전은 ONNX Runtime 기반이라 이 제한이 없습니다.

## 🚀 시작 방식

### dlib 버전

명령줄 인자로 설정하며, 어떤 환경변수도 읽지 않습니다. 기본으로 같은 위치의 `face_library`를 얼굴 라이브러리 디렉터리로 사용하고, 5000번 포트부터 수신합니다. 포트가 점유 중이면 자동으로 뒤로 밀리며, 최대 20개(5000–5019)를 시도합니다.

| 인자 | 기본값 | 설명 |
| --- | --- | --- |
| `--dir` | 스크립트 옆 `face_library` | 얼굴 라이브러리 디렉터리 지정, 모든 하위 디렉터리 재귀 스캔 |
| `--port` | `5000` | 시작 수신 포트 지정 |
| `--hog` | 꺼짐 | 페이지 기본 검출 모드를 「빠름」으로 설정; 페이지 드롭다운에서 언제든 되돌릴 수 있음 |
| `--library-info` | 꺼짐 | 얼굴 라이브러리 규모만 통계 출력 후 종료, 웹 서비스 미시작 |

```bash
python flask_face_match_v2.py --dir "D:\faces" --port 5000
python flask_face_match_v2.py --library-info          # 먼저 점검 후 배포
```

💡 `--library-info`는 첫 배포 시 사용하는 것을 권장합니다. 정식 서비스 전에 모델 로드 정상, 얼굴 라이브러리 경로 정확, 이미지와 얼굴 수가 기대치와 일치하는지 확인할 수 있습니다.

### InsightFace 버전

**어떤 명령줄 인자도 받지 않습니다** — 스크립트가 `sys.argv`를 전혀 읽지 않으며, 전달된 인자는 **조용히 무시**됩니다(오류도 없고 힌트도 없음). 이 때문에 인자가 적용된 것으로 오해하지 마세요. 얼굴 라이브러리 디렉터리는 시작 시 대화형으로 문의합니다:

| 프롬프트 | 설명 |
| --- | --- |
| 최초 시작 시 문의 | 얼굴 라이브러리 디렉터리 입력; 그냥 엔터를 누르면 스크립트 옆 `face_library` 사용 |
| 입력한 디렉터리가 없음 | 안내 후 다시 문의 |
| 디렉터리가 아닌 파일 입력 | 안내 후 다시 문의 |
| 비대화형 터미널 | 문의하지 않고 바로 기본 디렉터리 사용 |
| 기본 디렉터리 없음 | 자동 생성 (`mkdir(parents=True, exist_ok=True)`) |

시작 전 모델 로드와 한 번의 워밍업을 완료한 뒤 접속 가능 주소를 출력합니다. 최초 시작 시 `buffalo_l` 모델 패키지를 다운로드해야 하며, 소요 시간은 네트워크에 따라 다릅니다.

## 🔬 동작 원리

dlib 버전 처리 파이프라인:

> 🖼️ **입력 이미지** → RGB 배열로 디코드·정규화 → 얼굴 검출 → 68점 키포인트 정위 → 128차원 특징 추출 → L2 정규화 → 코사인 유사도 퍼센트 환산 → 정렬 후 Top-N으로 자르기

InsightFace 버전 처리 파이프라인:

> 🖼️ **입력 이미지** → 디코드·정규화 → SCRFD로 얼굴 검출 (`det_size=640×640`, `det_thresh=0.5`) 후 5점 키포인트 출력 → 크롭 및 정렬 → ArcFace로 512차원 특징 추출 → L2 정규화 → 코사인 유사도 퍼센트 환산 → 정렬 후 Top-N으로 자르기

점수에 대한 몇 가지 설명:

- 📏 점수는 **코사인 유사도 퍼센트**, 즉 `dot(a, b) × 100`입니다. 같은 이미지끼리의 자가 비교는 100%입니다.
- 🔎 **쿼리 이미지 측**은 최댓값 제한을 두지 않습니다: 각 후보는 쿼리 이미지 안의 **모든 얼굴**과 비교되며 최고 점수가 그 후보의 점수가 됩니다. 따라서 쿼리 이미지가 여러 사람의 단체 사진이어도 가장 닮은 얼굴을 정상적으로 고를 수 있습니다.
- 1️⃣ **후보 이미지 측**은 **면적이 가장 큰** 한 장의 얼굴만 비교에 사용합니다.
- 📊 결과 표의 바는 브라우저 단에서 0–100 구간으로 제한하여 그려지므로, 음수는 0% 빈 바로 표시되지만 숫자 라벨은 부호 있는 실제 점수를 보여줍니다.

> 📝 두 파일 모두 `face_similarity_percent()` 라이브러리 함수를 내보내며, 시그니처의 다중 얼굴 기본값이 **정반대**입니다: dlib 버전은 `compare_all_faces=False`(가장 큰 얼굴)를 기본으로, InsightFace 버전은 `largest_only=False`(최적 짝짓기)를 기본으로 합니다. 이 함수는 **어떤 HTTP 라우트에서도 호출되지 않으며**, 웹 동작은 위 규칙을 따릅니다.

## 📏 점수 기준

두 엔진의 특징 모델이 다르므로 점수는 **각자 내부에서만 비교 가능**하며, 엔진 간 비교는 의미가 없습니다.

| 샘플 | dlib 버전 | InsightFace 버전 |
| --- | --- | --- |
| 같은 이미지 자가 비교 | 100.00% | 100.00% |
| 같은 사람의 다른 사진 (정면 크롭 vs 반신 사진) | 96.85% | 77.57% |
| 다른 사람 (여러 샘플) | 같은 사람보다 현저히 낮음 | −3% ~ +1% |

위 표는 로컬 단일 샘플 실측값으로, 자릿수 차이를 설명하기 위한 것입니다. InsightFace의 ArcFace 특징은 서로 다른 사람 간의 구별도가 더 높아서, 같은 사람의 점수가 dlib보다 낮고 다른 사람의 점수는 0에 가깝습니다. 어느 쪽이 더 정확하다는 뜻이 아니라 스케일이 다를 뿐입니다.

💡 권장 방식: 하나의 엔진을 정한 뒤, 자신의 업무 시나리오에서 같은 사람/다른 사람 샘플을 각각 여러 조로 임계값을 보정하세요. 위 표의 숫자를 그대로 쓰지 마시고, 두 엔진의 점수를 같은 순위 목록에 넣어 정렬하지도 마세요.

## 🎛️ 검출 모드 (dlib 버전)

| 비교 항목 | 정확 (CNN) | 빠름 (HOG) |
| --- | --- | --- |
| 👁️ 검출기 | `mmod_human_face_detector.dat` | dlib 내장, 가중치 파일 불필요 |
| 🔍 업샘플링 횟수 | 0 | 1 |
| 🧩 적합 시나리오 | 옆얼굴, 작은 얼굴, 복잡한 배경 | 정면, 균일한 조명 |
| ⏱️ 상대 비용 | 높음 | 낮음 |
| 📍 키포인트 모델 | 동일 | 동일 |
| 🧬 특징 모델 | 동일 | 동일 |
| 📊 평가 로직 | 동일 | 동일 |

업샘플링이 한 단계 올라가면 소요 시간은 약 4배가 되며, 동시에 작은 얼굴의 검출률이 올라갑니다. 그래서 CNN 모드는 0, HOG 모드는 1을 사용합니다. 두 모드는 **얼굴 검출 단계에서만 차이가 있고**, 그 이후의 키포인트·특징·평가 체인은 완전히 동일하므로, 두 모드의 점수는 서로 직접 비교할 수 있습니다. 두 모드는 각자 특징을 캐시합니다(캐시 키에 검출 모드 포함). 왔다 갔다 전환해도 얼굴 라이브러리를 다시 인코딩하지 않습니다.

InsightFace 버전은 SCRFD 검출기만 있어 이 옵션을 제공하지 않습니다.

## 🗂️ 얼굴 라이브러리 약속

- 📍 **위치**: dlib 버전은 `--dir` 또는 기본 디렉터리로 결정; InsightFace 버전은 시작 시 응답 또는 기본 디렉터리로 결정. 둘 다 모든 하위 디렉터리를 재귀적으로 순회합니다.
- 🖼️ **형식**: `.jpg` `.jpeg` `.png` `.bmp` `.webp` 지원, 확장자는 대소문자를 구분하지 않음.
- 👥 **다중 얼굴 파일 (얼굴 라이브러리 검색)**: 한 장의 이미지 안의 **모든 얼굴**이 각각 독립 후보를 만들며, 두 번째부터 `#2`, `#3` 접미사가 붙음.
- 📤 **다중 얼굴 파일 (업로드 비교)**: 각 업로드 이미지에서 **면적이 가장 큰 얼굴 하나**만 사용하고, 접미사를 붙이지 않으며, 한 장에 얼굴이 여러 장이어도 후보를 쪼개지 않음.
- 🏷️ **동일 파일명**: 서로 다른 디렉터리의 같은 이름 파일은 **업로드 비교** 결과에서 「이름 (1)」「이름 (2)」로 구분하여 표시; ⚠️ 이 중복 제거는 **얼굴 라이브러리 검색에는 적용되지 않음** — 서로 다른 하위 디렉터리의 `zhang.jpg`는 라이브러리 검색에서 모두 `zhang.jpg`로 표시됨.
- ⚡ **캐시 전략**: 캐시 키는 파일의 절대 경로이며, 파일 수정 시각으로 유효성을 판정; 이미지의 수정·추가·삭제는 다음 검색 때 자동으로 반영되고, 삭제된 파일의 캐시 항목은 동기화하여 지웁니다. dlib 버전은 검출 모드도 캐시 키에 넣음.
- 🛡️ **내결함**: 이미지 읽기 실패나 얼굴 미검출 시 해당 항목은 건너뜀; 업로드 비교는 `skipped` 필드에 이유를 나열하고, 얼굴 라이브러리 검색은 조용히 건너뜀.
- 📊 **진행도 출력**: 얼굴 라이브러리 이미지 총수가 **20장 이상**이면, 두 버전 모두 터미널에 한 장씩 로드 진행을 출력 (캐시 히트 이미지도 마찬가지).
- 🏠 **디렉터리 생성**: InsightFace 버전은 시작 시 기본 얼굴 라이브러리 디렉터리를 자동 생성; dlib 버전은 디렉터리를 만들지 않으므로 스스로 준비해야 함.

- ⚡ 최초로 큰 얼굴 라이브러리를 검색하는 데 시간이 많이 걸립니다; 그 뒤에는 요청이 캐시에 적중하여 대개 밀리초 단위입니다. 캐시는 프로세스 메모리에 있으며, 서비스 재시작 후에는 무효화됩니다.

- 💡 InsightFace 버전은 검출기를 고를 필요가 없습니다; SCRFD는 입력 해상도에 민감하므로, 마찬가지로 라이브러리 전에 크기를 통일하는 것이 좋습니다.

> ⚠️ 위 수치는 하드웨어 구성, 이미지 크기, 이미지 내용에 따라 달라집니다. 배포 전에 반드시 목표 환경에서 직접 벤치마크하세요. InsightFace의 각 단계별 개별 소요 시간은 항목별로 따로 측정하지 않았습니다.

### 🧮 FAISS 검색 가속 관련

이 프로젝트는 **FAISS를 사용하지 않습니다**. 얼굴 라이브러리 검색은 NumPy의 정확한 행렬 곱(`라이브러리 내 얼굴 수 × 쿼리 얼굴 수`의 코사인 유사도)을 씁니다. 이는 의도된 선택입니다:

- FAISS의 `IndexFlatIP`는 **정확한** 인덱스이며, 현재 행렬 곱 결과와 완전히 일치하고 같은 일을 다른 방식으로 할 뿐이라 더 빠르지 않습니다. 실측에서 후보 500개의 유사도 계산 자체는 약 0.5 ms로, 병목이 아닙니다.
- 진짜 병목은 **얼굴 검출**에 있으며(위 표 참고), FAISS는 검출에 관여하지 않습니다.
- FAISS를 도입하면 약 456행의 의존성과 인덱스 수명주기 관리(추가·수정·삭제, 동기화, 영속화)가 늘어나지만, 이득은 거의 없습니다.

얼굴 라이브러리 규모가 **만 단위 이상**이고 실제로 검색 지연 때문에 막힐 때만, FAISS의 근사 인덱스(`IVF` / `HNSW`)로 바꿀 가치가 있습니다. 그때의 올바른 순서는 먼저 검출 비용을 낮추고, 그 다음 검색이 정말 병목인지 평가하는 것입니다.

## 🔌 HTTP 인터페이스

두 버전의 라우트와 응답 구조는 완전히 동일합니다. 모든 API는 무상태 호출입니다. 성공은 HTTP 200; 실패는 `ok: false`와 `error` 설명이 담긴 본문을 반환하며, 기본 상태 코드는 400, 요청 본문이 64 MB를 넘으면 413을 반환합니다.

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| GET | `/` | 웹 인터페이스 반환 |
| GET | `/api/library` | 얼굴 라이브러리 규모 통계, **수량만 반환, 디렉터리 경로는 반환하지 않음** |
| GET | `/api/health` | 준비 프로브: 이미지 수만 세고, **특징 추출은 하지 않음**, 고빈도 폴링 가능 |
| GET | `/api/stats` | 실행 설정: 특징 차원, 임계값 기준, 라이브러리 규모, 의존성 버전, 누락 모델 |
| POST | `/api/query-set` | 쿼리 이미지와 이번 업로드의 후보 이미지 비교 (1:N) |
| POST | `/api/query-library` | 쿼리 이미지와 얼굴 라이브러리 전체 비교 (1:N) |
| GET | `/library-image/<상대경로>` | 얼굴 라이브러리의 한 장 이미지 가져오기, 결과 표 썸네일용 |
| GET | `/library-image-download/<상대경로>` | 위와 같지만 다운로드로 반환 (`Content-Disposition: attachment`) |

> 📌 이미지 라우트는 **얼굴 라이브러리 내부**의 상대 경로만 받아들이며, `send_from_directory`가 파싱합니다. 라이브러리 디렉터리를 벗어나려는 어떤 방식(예: `../../`)도 거부됩니다(403/404). 라이브러리 디렉터리의 절대 경로는 어떤 응답에도 나타나지 않습니다.

### 🩺 `/api/health`

폴더 안의 이미지 수만 세고, 모델을 로드하거나 특징을 추출하지 않으므로 비용이 매우 작아 생존/준비 프로브로 적합합니다. `ready`가 `true`면 라이브러리에 이미지가 최소 한 장 있다는 뜻입니다. 그 이미지들에 정말 얼굴이 있는지는 실제 검색 때 알 수 있습니다.

```json
{ "ok": true, "ready": true, "images": 128, "detector": "cnn", "descriptor_dimension": 128 }
```

`detector`와 `descriptor_dimension`은 **dlib 버전만 반환**합니다.

### 📊 `/api/stats`

이 기기에서 **실제로 적용 중**인 설정을 반환하여, 「같은 이미지가 두 기기에서 점수가 다른」류의 문제를 진단하는 데 씁니다. 필드는 버전마다 약간 다르며, 공통 부분:

| 필드 | 설명 |
| --- | --- |
| `descriptor_dimension` | 특징 차원: dlib 버전 `128`, InsightFace 버전 `512` |
| `threshold_metric` | 임계값 기준, 고정값 `cosine_similarity` |
| `sort_order` | 정렬 방향, 고정값 `cosine_similarity_descending` (클수록 비슷) |
| `library_images` / `library_faces` | 라이브러리 내 이미지 수 / 검출된 얼굴 수 |
| `max_upload_mb` | 단일 요청 본문 상한(MB) |
| `missing_models` | 누락된 모델 파일명 목록, 비어 있으면 모델 완전 |
| `opencv_version` / `numpy_version` | 의존성 버전 |
| `detector` / `dlib_cuda` / `configuration` | **dlib 버전만** |
| `onnxruntime_version` / `onnxruntime_providers` / `model_directory_present` / `model_summary` | **InsightFace 버전만** |

### 🔧 공통 인자

| 인자 | 위치 | 값 | 기본값 | 적용 버전 |
| --- | --- | --- | --- | --- |
| `top_results` | 폼 또는 쿼리 문자열 | 정수, 1–100 범위 | 10 | 두 버전 |
| `detector` | 폼 또는 쿼리 문자열 | `cnn` 또는 `hog` | `cnn` | dlib 버전만 |

📌 `top_results` 규칙: **없거나 숫자가 아니면 → 10**; 정수로 파싱되면 → **경계값으로 자름** (1–100, `0` → 1, `999` → 100).

> ⚠️ 두 버전은 여기서 미세한 차이가 있습니다: dlib 버전은 `int()`로 파싱(`+5`, 앞뒤 공백 등 허용), InsightFace 버전은 `str.isdigit()`로 판정 후 변환(`+5`, 음수, 유니코드 숫자 불허). `top_results=-1` 입력 시 dlib 버전은 1건, InsightFace 버전은 10건을 반환합니다. 정상적으로 페이지에서 보내는 요청에는 영향이 없습니다.

> ⚠️ dlib 버전의 `GET /api/library`는 쿼리 문자열의 `detector`를 읽으므로, **같은 URL이라도 검출 모드에 따라 반환되는 `faces` 수가 달라질 수 있습니다**; InsightFace 버전은 이 인자를 무시합니다.

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `query` | 파일 | 예 | 쿼리 이미지, 단일 |

### ✅ 성공 응답 필드

| 필드 | 설명 |
| --- | --- |
| `ok` | 성공 여부 |
| `mode` | 검색 모드, `query-set` 또는 `query-library` |
| `query` | 쿼리 이미지 파일명 |
| `query_faces` | 쿼리 이미지에서 검출된 얼굴 수 |
| `detector` | 이번에 실제 사용한 검출 모드 (**dlib 버전만 반환**) |
| `count` | 이번에 제출된 후보 이미지 총수 (**업로드 비교만**) |
| `compared` | 특징 추출에 성공하여 비교에 참여한 후보 이미지 수 (**업로드 비교만**) |
| `library_images` | 얼굴 라이브러리 이미지 총수 (**얼굴 라이브러리 검색만**) |
| `library_faces` | 얼굴 라이브러리에서 검출된 얼굴 총수 (**얼굴 라이브러리 검색만**) |
| `matches` | 순위 결과 목록, `rank`, `kind`, `candidate`, `similarity` 포함, 첫 항목에 `best: true` 추가 |
| `skipped` | 건너뛴 후보 이미지와 이유 (**업로드 비교만**) |
| `elapsed_ms` | 서버 처리 소요 시간 (밀리초) |

`kind` 필드 값: `query-set`은 「후보 이미지」, `query-library`는 「라이브러리 후보」.

> 🖼️ `matches`의 각 행에는 `image_url`이 있을 수 있습니다: 해당 행 사진의 `/library-image/` 아래 주소를 가리키며, 페이지가 썸네일 표시에 씁니다. **얼굴 라이브러리 검색 (`query-library`)의 행만 이것를 가집니다**; 업로드 비교의 후보 이미지는 대응 파일이 없으므로 이 필드가 나타나지 않습니다.

## ⚠️ 알려진 제한

- 🚫 얼굴 검출 결과의 크롭·회전 보정 등 얼굴 정렬 보강을 제공하지 않음: dlib 버전은 기본 키포인트 예측만 사용, InsightFace 버전은 SCRFD 자체 5점 정렬 사용.
- 💾 특징 캐시는 프로세스 메모리에 있어, 서비스 재시작 후 전체 라이브러리를 다시 인코딩해야 함.
- 📏 특징은 각각 dlib ResNet(128차원)과 ArcFace(512차원)에서 나오므로, 다른 얼굴 인식 방식의 점수와 **직접 비교 불가**; 두 버전 간에도 비교 불가.
- 👥 업로드 비교 시 각 후보 이미지에서 면적이 가장 큰 얼굴만 사용하며, 단체 사진의 나머지 인물은 독립 후보가 되지 않음 (얼굴 라이브러리 검색은 각 얼굴을 펼침).
- 🚫 일괄 오프라인 비교 API와 결과 영속화 능력을 제공하지 않음.
- ⚡ 하드웨어 가속을 수동 지정 불가: dlib 버전은 로컬 검증 환경에서 CPU로 동작; InsightFace 버전은 시작 시 `CUDAExecutionProvider`를 자동 탐지하고, 가능하면 GPU 우선, 아니면 CPU 폴백. 사용자가 인자로 실행 장치를 강제 지정할 수 없음.
- 🐛 InsightFace 버전은 `top_results`의 비정상 유니코드 숫자(예: `²`) 처리가 미흡하여, 잡히지 않은 예외가 발생할 수 있음.

## ❓ 자주 묻는 질문

**❌ dlib 버전 시작 시 `.dat` 가중치 파일을 찾지 못한다고 나옴**
모델이 프로그램이 탐색할 수 있는 위치에 없음. [모델 파일](#-모델-파일-가중치-다운로드) 절을 참고하여 파일을 배치하거나, `face_recognition_models` 모델 패키지를 설치하여 앞의 두 필수 가중치를 해결하세요.

**❌ InsightFace 버전 시작 후 모델이 다시 다운로드됨**
스크립트 옆의 세 개의 `buffalo_l` 디렉터리와 `~/.insightface/models/buffalo_l`이 모두 `det_10g.onnx`와 `w600k_r50.onnx`를 동시에 포함하지 않음을 뜻합니다 — 불완전한 디렉터리는 조용히 건너뜁니다. 파일이 완전한지 확인하거나, 무인자로 실행해 시작 로그를 확인하세요.

**❌ 「얼굴 라이브러리에 이미지가 없습니다. 이미지를 넣은 후 다시 시도하세요」 안내**
얼굴 라이브러리 디렉터리가 없거나, 지원되는 이미지 형식이 없음. dlib 버전은 먼저 `--library-info`로 확인; InsightFace 버전은 다시 시작하여 안내 시 올바른 디렉터리를 입력.

**❌ 「쿼리 이미지에서 얼굴을 검출하지 못했습니다」 안내**
현재 검출기가 얼굴을 찾지 못함. dlib 버전은 「정확(CNN)」 모드로 바꿔 재시도를 권장 — CNN은 옆얼굴과 작은 얼굴에 더 관대합니다. 동시에 업로드한 것이 원본 사진인지, 스크린샷의 부분 크롭이 아닌지 확인하세요.

**❌ 「얼굴 라이브러리에서 얼굴을 검출하지 못했습니다」 안내**
얼굴 라이브러리에 이미지가 있지만 모두 얼굴이 검출되지 않음. 실제 검출 수를 먼저 확인하고, 이미지의 선명도와 크기를 표본 점검하세요.

**❓ 첫 검색은 느리고, 이후는 빠름**
예상된 동작입니다. 최초에는 전체 라이브러리를 인코딩해야 하고, 결과가 캐시되면 이후 요청은 밀리초 단위입니다.

**❓ 포트가 점유됨**
두 버전이 최대 20개 포트(5000–5019)를 자동으로 뒤로 밀어 씁니다. 터미널 출력의 실제 주소를 참고하세요.

**❓ 이미지를 교체했는데 검색 결과가 바뀌지 않음**
그래선 안 됩니다. 캐시는 파일 수정 시각으로 판정하므로, 라이브러리 안의 같은 경로 파일을 수정한 것인지 확인하세요.

**❓ 얼굴 라이브러리에 동명의 두 이미지가 모두 `zhang.jpg`로 표시됨**
현재 구현이 그렇습니다. 「이름 (1)」「이름 (2)」중복 제거는 **업로드 비교** 결과에만 적용되고, 얼굴 라이브러리 검색은 중복 제거를 하지 않습니다.

**❓ 가중치 파일이 비ASCII 문자가 포함된 경로에 있어도 사용할 수 있나**
가능합니다. dlib 버전은 자동으로 모델을 시스템 임시 디렉터리에 복제한 뒤 로드합니다; InsightFace 버전은 이 제한이 없습니다. 프로그램은 여러 후보 경로 중 순수 ASCII 우선으로 선택합니다.

**❓ 왜 어떤 후보는 점수가 없거나 결과에 나타나지 않나**
해당 이미지 읽기 실패이거나 얼굴이 검출되지 않았습니다. 업로드 비교의 응답에서 `skipped` 필드가 이유를 나열합니다; 얼굴 라이브러리 검색은 조용히 건너뛰며, `--library-info`로 이미지 수와 얼굴 수를 대조할 수 있습니다.

**❓ 두 버전의 점수를 함께 비교할 수 있나**
불가능합니다. [점수 기준](#-점수-기준)을 참고하세요. 두 버전의 스케일이 다르므로 각각 임계값을 보정해야 합니다.

**❓ 로컬 네트워크의 동료가 이 페이지를 열 수 없음**
두 버전이 기본 `0.0.0.0`에 바인딩되어 이론상 접근 가능; 연결할 수 없으면 시스템 방화벽이 해당 포트를 허용하는지 확인하세요.
